## The Storage Layer: Why SQLite?

Before starting the project, I first analyzed what I would actually require, and the first thing that came to me was local persistent storage. Since it is supposed to be used by a developer continuing their chat session on the same computer across different IDEs, I chose **SQLite**.

### Why SQLite?

SQLite is a very lightweight SQL database that stores everything inside a single local file. It does not require any background database server process. Since it operates as direct local file reads and writes, it is extremely fast and a perfect match for a desktop MCP server.

---

## Schema Design

I bifurcated the storage model into 3 core relational tables:

1. **`sessions`:** Stores session ID, friendly name, project tech stack snapshot, and timestamps.
2. **`messages`:** Stores message history (user and assistant roles, content, source IDE, timestamp).
3. **`memories`:** Stores explicit key decisions, facts, and developer rules.

### Database Schema

```sql
CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  project_snapshot TEXT DEFAULT '',
  created_at INTEGER NOT NULL,
  last_updated INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content TEXT NOT NULL,
  source_ide TEXT DEFAULT 'unknown',
  timestamp INTEGER NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);

CREATE TABLE IF NOT EXISTS memories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id TEXT NOT NULL,
  memory TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);
```

### Why Composite Indexing?

Loading a session requires querying all messages and memories associated with a `session_id`. Without indexes, querying would require full table scans ($O(N)$ complexity). 

By adding **composite indexes** on `(session_id, timestamp)` and `(session_id, created_at)`, query retrieval speed improves to $O(\log N)$ logarithmic time:

```sql
CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, timestamp);
CREATE INDEX IF NOT EXISTS idx_memories_session ON memories(session_id, created_at);
```

## The MCP Tools Implementation

In the Anthropic MCP SDK, an MCP Tool consists of four core elements:

1. **Name:** Unique tool identifier string (e.g. `create_session`).
2. **Description:** Descriptive string guiding the LLM on when to invoke the tool.
3. **Validation Layer:** Zod schema enforcing parameters generated by the LLM.
4. **Service:** Async handler function executing database operations and returning tool output.

### Tool Registration Example: `create_session`

```typescript
import { z } from 'zod';

export const createSessionSchema = z.object({
  id: z.string().describe("Unique identifier for the session (e.g., 'auth-service')"),
  name: z.string().describe("A friendly name for the session"),
  project_snapshot: z.string().describe("Summary of the tech stack and project state"),
});

export function createSession(args: z.infer<typeof createSessionSchema>) {
  const now = Date.now();
  const statement = db.prepare(`
    INSERT INTO sessions (id, name, project_snapshot, created_at, last_updated)
    VALUES (@id, @name, @project_snapshot, @created_at, @last_updated)
    ON CONFLICT(id) DO UPDATE SET 
      name = excluded.name, 
      project_snapshot = excluded.project_snapshot, 
      last_updated = excluded.last_updated
  `);

  const sessionData = {
    ...args,
    created_at: now,
    last_updated: now,
  };

  statement.run(sessionData);
  return sessionData;
}
```

## The Core Handoff Engine: `get_session`

The most important tool in the server is `get_session`. It fetches data from all three tables and constructs a structured handoff prompt that is returned to the new IDE's LLM context window:

```typescript
export function generateHandoffPrompt(sessionId: string, messageLimit: number = 20): string {
  // 1. Fetch basic session info
  const session = db.prepare("SELECT * FROM sessions WHERE id = ?").get(sessionId) as Session | undefined;
  
  if (!session) {
    throw new Error(`Session ${sessionId} not found.`);
  }

  // 2. Fetch memories (key decisions/facts)
  const memories = db.prepare("SELECT memory FROM memories WHERE session_id = ? ORDER BY created_at ASC").all(sessionId) as Memory[];

  // 3. Fetch recent messages (last N)
  const messages = db.prepare("SELECT role, content FROM messages WHERE session_id = ? ORDER BY timestamp DESC LIMIT ?").all(sessionId, messageLimit) as Message[];
  messages.reverse(); // Restore chronological order

  // 4. Build Handoff Prompt String
  let prompt = `--- SESSION HANDOFF: ${session.name} ---\n\n`;
  prompt += `## PROJECT SNAPSHOT\n${session.project_snapshot || "No snapshot provided."}\n\n`;

  if (memories.length > 0) {
    prompt += `## KEY DECISIONS & MEMORIES\n`;
    memories.forEach((m, i) => {
      prompt += `${i + 1}. ${m.memory}\n`;
    });
    prompt += `\n`;
  }

  if (messages.length > 0) {
    prompt += `## CONVERSATION HISTORY (Last ${messageLimit} turns)\n`;
    messages.forEach((msg) => {
      const roleName = msg.role === "user" ? "USER" : "ASSISTANT";
      prompt += `[${roleName}]: ${msg.content}\n`;
    });
    prompt += `\n`;
  }

  prompt += `--- END OF HANDOFF ---\n`;
  prompt += `You are now continuing this session. Please review the context above and wait for the user's next instruction.`;

  return prompt;
}
```

## Conclusion

A SQLite database, a set of modular MCP tools, a structured handoff prompt generator, and the Anthropic MCP Client framework doing the heavy lifting behind the scenes. Building an MCP server is essentially as simple as defining your schema and tools, letting the AI host handle invocation seamlessly.
